# Nukkad — Data Model & Supabase

Deep reference for `packages/db/prisma/schema.prisma` and the Supabase deployment. The schema is heavily commented in-place; this doc explains the *system* of it — what we store, why each table exists, and how the database is operated.

## How Supabase is wired

One Supabase Postgres project (region: Seoul; host `db.durqvjrbihmerdngshsu.supabase.co`) holds everything. Prisma is the only access path from the app. **Three connection routes, each with one job:**

| Route | Port | Used by | Why |
|---|---|---|---|
| **Transaction pooler** (pgbouncer) | 6543 | App runtime (`DATABASE_URL`) with `?sslmode=require&pgbouncer=true&connection_limit=6&pool_timeout=30` | Survived the pool-exhaustion incident (ADR-020). Transaction-mode pooling multiplexes many app connections over few server slots. |
| **Session pooler** | 5432 (pooler host) | formerly runtime | IPv4-answerable (survives venue wifi/ngrok/CI) but capped at 15 sessions; Prisma's default pool (CPUs×2+1) across several node processes exhausted it → `EMAXCONNSESSION`. Abandoned for runtime. |
| **Direct host** | 5432 | `DIRECT_URL` — Prisma migrate/DDL only; also Evolution API's own Prisma | IPv6-only; migrations need a real session. Never used by the app at runtime. |

Ops facts learned the hard way: an `EMAXCONNSESSION` mentioning "session mode" usually means a **stale/zombie node process** is holding slots — cure `taskkill /f /im node.exe`, restart; occasional `P1001` (can't reach DB) in test suites is network flake to Seoul, not a code bug — rerun before patching anything. The **Evolution API** gateway (see [CHANNELS-WHATSAPP.md](./CHANNELS-WHATSAPP.md)) shares this database but is fully isolated in its own Postgres schema via `?schema=evolution` on its connection string — its ~30 tables never touch ours.

## The schema, as a system

The tables group into seven organs. Everything money- or eval-critical keeps *verbatim* source text and never overwrites it.

### 1. Parties
**`Kirana`** — the shop: name, owner, unique phone, plus the per-shop WhatsApp identity that is the multi-tenant boundary (`whatsappNumber`, `wabaId`, `phoneNumberId`, `wabaStatus` PENDING→QR_ISSUED→CONNECTED→FAILED, `onboardedAt`). Inbound routing is by *which number the customer messaged*, never by the customer. The schema comment forbids Baileys-style QR onboarding for production shops (ban risk); production onboarding is Meta COEXISTENCE. **`Household`** — a customer family under a kirana: phone (unique per shop), memberCount, address, and the autonomy machinery: `autonomyTier` (MANUAL / SUGGESTED default / STANDING / SILENT), `streak` (consecutive correct predictions gating promotion — autonomy is *earned by measured accuracy*), `vetoWindowMins` (tier 2), `capPaise` (tier 3 rupee ceiling). **`Supplier`** — the other end of the shop's WhatsApp: name + phone only, deliberately *not* a supplier→SKU catalogue (a kirana knows which distributor to call; encoding it wrong sends an order to the wrong shop). **`ShopUser`** — owner login, deliberately thin: phone + OTP hash.

### 2. Catalogue
**`Sku`** — name, brand, packSize/unit, `mrpPaise`, `sellPaise`, `costPaise` (from the latest supplier bill, so margin is computable), `category` (feeds same-category basket correction — a NULL here once silently broke corrections), and inline `aliases[]` ("chakki atta", "peela tel" — the cheapest accuracy win in the system). **`Stock`** — one quantity per SKU. **`SkuAlias`** — the bridge between trade language and household language, the single highest-leverage data in the system: `source` OWNER / LLM_SUGGESTED / LEARNED, `approved`, `hitCount` (how many orders it actually resolved). Never typed from scratch: suggested at bill import (auto-approved, because the owner reviewed the plan) or typed by the owner. **Caveat:** the schema comment promises `LEARNED` aliases from customer disambiguation taps, and `hitCount` promises usage tracking — neither is implemented; both are written nowhere in code. **`ProductKb`** — the retrieval corpus: canonical + brand (empty string, never null — Prisma can't put a nullable in a compound unique) + category + `subnames[]` (lowercase Roman Hinglish, most-said first) + flattened `searchText` for trigram search. Exists so alias generation *retrieves* instead of free-recalling.

### 3. Orders & money — two states, never one
**`Order`** — goods state (`OrderStatus`: DRAFT / AWAITING / PAYMENT_PENDING / CONFIRMED / CANCELLED / FULFILLED) *and separately* money state (`PaymentStatus`: PENDING / SUCCESS / FAILED / EXPIRED), because "paid but still packing" and "packed but unpaid on udhaar" are both ordinary kirana days and one enum cannot say both. `paidAt` is set only when a *verified* payment lands — never from a message. Replay fields (`rawText`, `transcript`, `asrEngine`, `mediaPath`, `latencyMs`) let any order re-run through the eval harness. **`OrderLine`** — `sourceText` verbatim (the eval harness diffs against it; never overwrite), quantity/unit hint, prices, and the resolution audit: `method` (EXACT / FUZZY / PRIOR / EMBEDDING / LLM / DISAMBIGUATED / SUBSTITUTED / UNRESOLVED), `confidence`, substitution provenance, and `alternatesJson` (the top-k offered, so a rejected suggestion is still analysable). **`Invoice`** — one per order: amount, paid amount, Razorpay link id + short URL, our `referenceId` (sent as Razorpay's reference_id, unique), and the udhaar mechanic: `acceptPartial` + `firstMinPartialPaise` — partial payment *is* credit with a paper trail, no beta APIs. **`Payment`** — one row per captured Razorpay payment (unique `razorpayPaymentId`, raw JSON kept). **`DistributorInvoice`** — the shop→distributor leg, where a payment link is genuinely wanted (wholesale amounts, collection); at household sizes direct UPI (0% MDR since Jan 2020) competes. **`WebhookEvent`** — raw events keyed `(source, externalId)`; Razorpay retries webhooks, Twilio retries webhooks, and this table makes every retry a no-op.

### 4. Bills (onboarding)
**`SupplierBill`** — the uploaded photo, status machine UPLOADED→PARSED→PLANNED→REVIEWED→COMMITTED (or FAILED), supplier/billNo/date/total, `docType` PURCHASE / RETAIL / UNKNOWN (a retail receipt applied as a purchase silently inflates stock by exactly what left the shelf — direction is detected and retail confirmed by the owner), vision model + timings. **`SupplierBillLine`** — `rawName` verbatim (the review screen diffs on it) beside `workingName` (Roman working form) and `gloss`; quantity/rate/amount plus the full GST decomposition (`listPricePaise`, `discPct`, `taxPct` — `amount = qty × list × (1−disc%) × (1+tax%)`, all printed, none equal to amount/qty, each kept so "list 400 + 5% GST → 420" explains itself); `mrpPaise` kept distinct from rate (retail bills discount off MRP); `isFree` (quantity with no amount — never priced, never counted); `derived[]` (which of qty/rate/amount we *solved for* rather than read — shown as our arithmetic, not their paper); the agent's verdict `decision` (RESTOCK / NEW / AMBIGUOUS / SKIPPED) + `confidence` + one-sentence `reasoning` ("an agent that cannot say why it matched something is an agent nobody should let write to a catalogue") + `candidatesJson` (every retriever candidate with scores, so a wrong call is auditable); `disputed` + `disputeNote` (two readings disagreed or qty×rate ≠ amount → forced AMBIGUOUS, because a misread digit on a handwritten bill looks like a price, not an error); `suggestedAliases[]`; price movement (`priceDeltaPaise` vs last paid, `proposedSellPaise` carried from the old margin so a shop's pricing survives a restock). **`BillAgentStep`** — one row per agent-graph node execution (seq, node, OK/RETRY/FAIL/SKIP, ms, note, detail) — persisted rather than logged because the review screen *replays* it for the owner and for judges.

### 5. Prediction
**`BurnRate`** — the whole depletion model in one float: `qtyPerDay` per household×SKU, `predictedDepletionAt`, `observations` (0 = still the HCES survey seed) and `seeded`. **`Nudge`** — one row per proactive knock: template, sent/responded timestamps, outcome (ACCEPTED / EDITED / DECLINED / IGNORED / VETOED), and `predictedBasketJson` vs `resultingOrderId` — the depletion-accuracy row of the ablation table, generated by operation.

### 6. Messaging
**`Conversation`** — unique per (channel, peerPhone), party role (HOUSEHOLD / KIRANA / SUPPLIER), state machine (IDLE / MENU / AWAITING_ORDER_INPUT / AWAITING_CONFIRM / AWAITING_DISAMBIGUATION / AWAITING_VETO), `contextJson` (the conversation-engine `Convo` state: desk, basket, pending, lastNamed, lastAt), and `windowExpiresAt` — Meta's 24-hour session window; past it, only a pre-approved template may be sent, and the nudge scheduler MUST check it before composing anything. **`Message`** — direction, `externalId` (transport message id → idempotency via unique `(conversationId, externalId)`; Twilio and Meta both retry), body/media/transcript, `templateName`, and the two-axis annotation `intent`/`goal` (MG-ShopDial, SIGIR '23 — nullable, additive, off the critical path).

### 7. The intelligence spine
**`UnmetDemand`** — what the shop was asked for and could not sell: verbatim `query`, `confidence` (how close the resolver got), `offered` (what was suggested instead). Written by the seller desk the moment resolution fails; read by nobody during the call — the "inventory intelligence agent" *is* the aggregation query over this table. **`Offer`** — deterministic promotions (title, `minBasketPaise`, `flatOffPaise`, active, expiry): "koi offer chal raha hai?" is answered from these rows and never from a model's imagination, because an invented discount is a real rupee loss. **`AgentEvent`** — one row per turn (kirana, household, channel, desk, act, goal, heard, reply, handoffFrom/To, latencyMs), written fire-and-forget at the end of `handle()`; every workforce metric, customer timeline, and conversation drill-down on the dashboard is a view over these rows — never a reconstruction. **`RestockAction`** — the closed loop on unmet demand: query, status OPEN → ORDERED / IGNORED / STOCKED. Customer asks → agent cannot fulfil → ledger → recommendation → this row tracks what happened next.

## Query surfaces over this data

`routes/analytics.ts`: `/analytics/insights` (demand grouped by `normalise()` with times/households/lastAsked/offered; top products; low stock), `/analytics/demand/detail?q=`, `/analytics/product/detail?skuId=`. `routes/intelligence.ts`: `/intel/attention` (red: stock ÷ velocity ≤ 3 days; orange: unmet asked ≥ 2×; green: customer overdue past 1.25× their median order gap), `/intel/customers`, `/intel/customer/detail` (median gap, frequent items, AgentEvent timeline, category-gap opportunity), `/intel/conversations`, `/intel/workforce` (per-desk turns/latency/handoffs/top acts), `/intel/restock` GET/POST + `/intel/restock/status`. The standing refusal: no invented numbers — e.g. no revenue estimate for demand the shop has never stocked.

## Seeds and known data caveats

Seeds provide the demo kirana, households (test household phone +91 89795 60165 "Ramesh"), a catalogue, KB rows, offers, and historical orders. Two lessons already paid for: a seeded SKU with `category` NULL silently disabled same-category correction (categories are data the engine relies on); and some seeded order quantities are absurd enough to distort velocity-based attention cards (a sanity clamp is an open item). When a dashboard number looks insane, suspect the seed before the query.
