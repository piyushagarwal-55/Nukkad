# Nukkad — Retrieval, RAG, Matching and Ranking

How a customer's words become a SKU. Every threshold, weight and formula below is quoted from the code with its file and line, and every "measured" number is one recorded in the source as a real observation.

---

## The headline answers

| Question | Answer |
|---|---|
| Is there vector/embedding search? | **No.** No pgvector, no embedding calls anywhere. `ResolutionMethod.EMBEDDING` exists as a dead enum member only. |
| Is there RAG? | **Yes — trigram RAG over Postgres**, used by the bill agent, alias generation, category elicitation and the "we don't stock that" answer. |
| Is `pg_trgm` used? | Yes, in exactly two raw SQL queries. The *conversational* resolver does not use SQL at all — it ranks in-process over a cached catalogue. |
| Where does the corpus live? | `ProductKb`: **426 rows, 1,665 subnames, 18 categories**, seeded from `packages/shared/src/constants/product-kb.ts`. |
| Ask-or-guess threshold | `confidenceFloor = 0.55` in conversation; `MATCH.AUTO = 0.62` / `MATCH.REVIEW = 0.30` in bills. |
| "2 kg" when the shop sells 5 kg packs | `fitPack` → ratio 0.4 → `exact: false`, `units: 1` → **the shop says so and lets the customer decide**. Never silently rounded. |

**Why trigrams and not embeddings**, stated in `kb/retrieve.ts:6-12`: vector search earns its keep on long prose, but these failure modes are character-level — case, spacing, abbreviation, a missing vowel. And Groq serves no embedding model, so a vector path would mean a second vendor for a worse result.

---

## Two independent retrieval systems

They share no code and use different algorithms, because they answer different questions.

**System A — Postgres trigram RAG** (`services/kb/retrieve.ts`). Used by the bill agent, grounded alias generation, category elicitation. Algorithm: `pg_trgm` `similarity()` / `word_similarity()` in raw SQL.

**System B — in-process lexical ranker** (`services/resolver/*`). Used by **every inbound customer message**. Algorithm: token-set Levenshtein over an in-memory cached catalogue, plus a household prior. Never issues a similarity query.

The bridge is `openCategory()` (`core.ts:1447`): System A supplies canonical product *names*, System B ranks those names against this shop's shelf.

## System A — the trigram RAG layer

### The KB query (`kb/retrieve.ts:138-145`)

```sql
SELECT id, canonical, brand, category, unit, subnames,
       GREATEST(similarity("searchText", $1), word_similarity($1, "searchText")) AS score
  FROM "ProductKb"
 WHERE GREATEST(similarity("searchText", $1), word_similarity($1, "searchText")) > 0.08
 ORDER BY score DESC, similarity("searchText", $1) DESC
 LIMIT $2
```

**Why `GREATEST` of two measures.** `similarity()` divides by the trigram *union*, so adding subnames to a KB row made that row **harder** to retrieve — the documented regression: *"atta" against a KB entry carrying nine subnames returned Maida, Bajra Atta and Makki Atta, and never surfaced Whole Wheat Atta at all.* `word_similarity()` fixes that by scoring the best matching *window*. Measured deltas recorded in the file (`retrieve.ts:129-131`):

| bill line | before | after | matched |
|---|---|---|---|
| AASHIRVAAD SELECT ATTA 5KG | 0.33 | **0.58** | Whole Wheat Atta |
| TATA TEA GOLD 500 GM | 0.22 | **0.42** | Tea Leaves |
| SURF EXCEL … DETERGENT 1 KG | 0.46 | **0.71** | Detergent Powder |

The tie-break (`similarity(...) DESC`) exists because `word_similarity` saturates at 1.00 on short queries — *"five flours all score 1.00"*.

Input is cleaned by `normaliseBillName()` (`retrieve.ts:87-95`): strip quantities, strip packaging noise (`rfd|refined|pouch|packet|jar|tin|box|bag|btl|bottle|pkt`), strip non-alphanumerics, collapse whitespace.

### The SKU query (`kb/retrieve.ts:172-183`)

Same shape against this shop's own catalogue, scoring **best-of(name, best alias)** via `unnest(s.aliases)` + `MAX`. Note: **no score threshold** — it always returns up to 5 rows even at score 0, and filtering is the caller's job.

### Decision thresholds (`kb/retrieve.ts:197-204`)

`MATCH.AUTO = 0.62` (restock without asking) · `MATCH.REVIEW = 0.30` (below this, create a new SKU) · `MATCH.RUNNER_UP_GAP = 0.12` (two candidates this close → ask the owner).

### The corpus (`packages/shared/src/constants/product-kb.ts`)

240 hand-written entries + 186 generated by `expandBrands()` over 36 product families × 187 brand names = **426 rows** carrying **1,665 subnames** across 18 categories (flour, rice, pulses, oil, staple, beverage, spice, dairy, bakery, snacks, dryfruit, condiment, homecare, personal, baking, disposable, vegetable, pooja). Hand-written entries always win collisions. `searchText` is `canonical + brand + subnames` lowercased and flattened for trigram search.

The corpus is retrieved for five distinct jobs: grounding alias generation (k=4), transliteration-vs-gloss agreement checking (k=1 each), evidence attached to bill lines (k=4), category elicitation (k=8), and "we don't stock that" recognition (k=1).

### Where the "G" in RAG happens (`services/bills/subnames.ts`)

Alias generation *retrieves before it generates*. `retrieveKb()` builds a REFERENCE block (`- {brand} {canonical} ({category}): {subnames}`) and the prompt says **"Prefer names that appear in the REFERENCE block. Reuse them verbatim"** and **"NEVER include the pack size or a number"**. Temperature 0.2, max 8 aliases of 2–40 chars, and a post-filter drops any alias containing a digit. `grounded: !!reference` is recorded so the bill agent can report how many lines had KB backing. Asked cold, a model invents subnames nobody says; given the real ones for the nearest known products, it stays on the ground.

### Known issue: the GIN indexes are decorative

`kb-seed.ts:21-27` creates `pg_trgm` and two `gin_trgm_ops` indexes. But a GIN trigram index accelerates the `%` operator and `<->` distance — **not** a bare `similarity(a,b) > 0.08` predicate wrapped in `GREATEST(...)`. Worse, `sku_name_trgm` indexes `name` while the query filters `lower(s.name)`, and the alias branch scans `unnest()`, which no index covers. Both queries sequential-scan. At 426 KB rows and a few hundred SKUs this is fast enough, but the indexes as written do nothing.

## System B — the conversational ranker

### Step 0 — mask the commands (`resolver/action.ts`)

18 Hinglish command phrases, **sorted longest-first** so `"cancel kar do"` beats `"kar do"`: `cancel kar do, hata do, nikal do, add kar do, pack kar do, daal do, daal dijiye, daal dena, rakh do, rakh dijiye, de do, de dijiye, kar do, bhej do, bhej dena, bhej dijiye, ek aur, aur do`. `"ek kilo sugar daal do"` leaves `"ek kilo sugar"`; `"haan daal do"` leaves **nothing** — and that empty remainder is the signal that this message points at something rather than naming it. The file's own constraint: *"It is not a list of products, and it must never become one. This is grammar."*

### Step 1 — normalise (`resolver/normalise.ts`)

Thirteen folds, applied in order: `aa+→a`, `ee+→i`, `oo+→u`, `ii+→i`, `kh→k`, `gh→g`, `dh→d`, `th→t`, `bh→b`, `ph→f`, `w→v`, `z→j`, `ck→k`, `y$→i`. Twenty stop-words dropped (`wala wali vala vali wo vo ye yeh ka ki ke ek aur bhi bhej dena do chahiye packet pack`), plus single characters. The file's claim: *"worth more than any embedding model on a 400-item catalogue."*

### Step 2 — score (`resolver/fuzzy.ts`)

Levenshtein, two-row iterative. A query token counts as matched only at **≥ 0.70** (*"below 0.7 is noise, not a near-miss"*). Then:

```ts
coverage = sum(best per matched token) / tokenCount
whole    = ratio(normalise(query), normalise(target))
score    = 0.75 * coverage + 0.25 * whole
```

`matched` — how many query tokens were found — becomes **specificity**, which breaks ties later.

### Step 3 — morphology rescue (`resolver/morphology.ts`)

```ts
word.replace(/([a-z])\1+/g, '$1')   // degemination: atta → ata
    .replace(/e$/, 'a');            // oblique case: aate → aata
```

The bug that forced it: *"Aate ka price kya hai?" scored **0.017** against "Aashirvaad Whole Wheat Atta 5kg". Not a near miss — zero.* And the reason it is a **gated rescue tier and not part of `normalise()`**: these same folds move `chini→chana` and `chai→cha`, so applied globally they break matches that were already right. The gate (`rank.ts:296-299`): run recovery only when no claim reached 0.70, and adopt the rescued set only if it clears 0.70.

### Step 4 — rank (`resolver/rank.ts`), and every constant

| Constant | Value | Governs |
|---|---|---|
| `confidenceFloor` | **0.55** | ask vs act |
| `topK` | 3 | candidates kept |
| `MIN_LEXICAL_FOR_PRIOR` | 0.20 | prior may not vote below this |
| `TIE_EPSILON` | 0.02 | what counts as tied |
| `ALT_BAND` | 0.85 | alternate admission (on `fuzzy`) |
| `RECOVERY_TRIGGER` | 0.70 | morphology gate |
| `W_FUZZY` / `W_PRIOR` | 0.70 / 0.30 | final score blend |
| inclusion cutoff | 0.05 | minimum to appear at all |
| confidence blend | 0.6 × score + 0.4 × margin | how sure we are |

The pipeline: strip quantity words (44 entries including `ek do teen char paanch chhe saat aath nau das adha dedh dhai sava`) → collect a claim per SKU over `[name, brand, ...aliases]`, keeping the best *single* name's score and specificity together → compute `particularity = specificity + explains` (the reverse-direction match count) → recovery gate → prior eligibility → `score = 0.7·fuzzy + 0.3·prior` → sort by score then specificity → **reorder** near-ties by specificity (a reorder rather than a comparator, because a near-equal comparator is non-transitive) → confidence from score and margin.

**`ALT_BAND = 0.85` was measured, not chosen** (`rank.ts:78-90`):

| utterance | top | runner-up | ratio | verdict |
|---|---|---|---|---|
| daal kaunsi kaunsi hai | Toor .786 | Moong .704 | .90 | peer |
| daal kaunsi kaunsi hai | Toor .786 | Tea .598 | .76 | noise |
| atta hai kya | Atta .833 | Tea .625 | .75 | noise |
| moong dal ka price | Moong .830 | Toor .780 | .94 | peer |

**Ask-or-act** (`rank.ts:443-446`): disambiguate when nothing was chosen, or when confidence is below the floor — **unless there is exactly one exact match**. Multiple exact matches do *not* bypass the floor, because three rices all answer to "chawal".

### The household prior (`resolver/prior.ts`)

Last 500 order lines from CONFIRMED/FULFILLED orders, weighted by exponential decay with a **45-day half-life**, then log-normalised against `max(1, ...)` so a household with one order doesn't get a prior of 1.0. Cached 60s (measured cost before caching: **~700ms per turn**).

**The prior only arbitrates; it never overrules.** It applies only to candidates within `TIE_EPSILON` of the lexical leader, with equal-or-better particularity, and at least `0.20` fuzzy — so its maximum contribution is **+0.30** on a tie. This rule came from a measured inversion (`rank.ts:309-312`): *"the ablation inverted: catalogue-only rose to 86% and adding the prior DROPPED it to 71%, because history was overruling the lexical evidence rather than arbitrating it."* Alternates are banded on **`fuzzy`, not `score`**, so the prior cannot smuggle a rival onto the list either.

### Pointers and referents (`resolver/resolve.ts`)

21 pointer words (`yeh ye yah wo woh vo ise isko iske usko uske usi isi this that it same wahi yehi`) and ~40 fillers. The whole message is masked **first**, then spans are judged. When nothing productish survives and there is a referent, the resolver returns the referent **SKU by id** — never re-matched by name — with score 1 and specificity 99. When there is no referent, it returns `line: null` so the caller **asks**: *"inventing a search at this point is how 'yeh' became dry yeast."*

`pickFrom()` — choosing from a small offered set — deliberately runs with `usePrior: false` (*"what they usually buy has no vote in that"*), floor 0.40, gap 0.15, and deliberately does **not** reuse `needsDisambiguation`, because *"'sugar nahi chahiye' scores Sugar at 0.50 and Atta at nothing"* and the caller once read that as refusing the whole order.

### Pack fitting (`resolver/pack.ts`)

The damage this prevents, quoted from the file:

```
paper: Flour 5 kg    ordered: 5 × Aashirvaad Atta 5kg    (25 kg)
paper: Tea   500 g   ordered: 250 × Tata Tea Gold 500g   (125 kg)
total: Rs 79,055.65
```

`declaredPack()` prefers `sku.unit` when it is a mass/volume unit, else parses the **name** — because a SKU created from a bill has `packSize=1, unit=pc` but `"Basmati Rice 5kg"` in its name. `fitPack()` computes `ratio = want.base / pack.base`; an exact whole multiple (within 0.01) passes silently; anything else returns `units = max(1, ceil(ratio))` with **`exact: false`**. The rule: **round up, never down, and flag it.**

Worked on the real photo: `2 kg` of rice against a `5 kg` pack → ratio 0.4 → `units = 1`, `exact = false` → *"Aapne 2 kg kaha, ye 5 kg ke packet mein aata hai."*

### Substitution (`services/substitution/substitute.ts`)

Hard filters first: in stock, same category, **same unit exactly**, pack within 20%, price within 25%. Then `score = 0.35·(1−priceDelta) + 0.25·(1−packDelta) + 0.40·prior` — **familiarity is the heaviest weight**. Substitutes are given `fuzzy: 0` and `specificity: 0` deliberately: *"A substitute has no lexical claim on what was said"*, which keeps them out of `ALT_BAND` comparisons. Top 3 offered.

### What the extractor is *not* allowed to do (`services/extraction/extract.ts`)

The model segments the sentence and pulls quantities. **It does not pick the SKU** — *"You do NOT pick products from any catalogue. Something downstream does that."* The stated reason: *"Letting a language model name the product is the failure mode that caps open-menu voice ordering around 86 percent even in clean English."*

## The full fallback ladder

```
exact name or alias
  → conservative fuzzy (≥0.70 per token)
  → morphological recovery (only if nothing reached 0.70)
  → ask the customer (max 2 asks, then take alternates[0])
  → openCategory: KB k=8 → rank each against this shop → keep fuzzy ≥0.5 AND in stock → offer 2–4
  → KB k=1 recognises it but the shop doesn't stock it → "NOT_STOCKED" + UnmetDemand row
  → "samajh nahi aaya"
```

`openCategory()` deliberately does **not** join on category, because *"the two vocabularies are unrelated. The KB files things under snacks, pooja, homecare; a shop's own catalogue says wheat_atta, edible_oil, biscuit."* It scores on `fuzzy` rather than `confidence`, because margin collapses exactly when a shop has three attas.

## Caching

`getCatalog` 5 minutes, `getStockMap` 10 seconds, `buildPrior` 60 seconds — all invalidated explicitly on settlement. The motivation is geographic: Supabase sits in `ap-northeast-2` and a query from India measures **~296ms**; the stock re-read alone was 300ms per turn.

`Sku.aliases` is a **denormalised `String[]`** rebuilt from approved `SkuAlias` rows by `catalog/aliases.ts`, which then invalidates the catalogue cache. The contract: *"Anything that touches SkuAlias MUST call this afterwards."*

## Corrections to earlier claims in these docs

Two things the schema comments promise that the code does **not** yet do. They are listed here rather than quietly left in place.

1. **The learning loop is not implemented.** `AliasSource.LEARNED` is declared in the schema and documented as *"when the resolver is unsure and the buyer taps a disambiguation option, that is a labelled example and becomes an alias"* — but `LEARNED` appears in **no TypeScript file**. The disambiguation handler sets `method = 'DISAMBIGUATED'` and `confidence = 1` and writes no alias. Likewise `SkuAlias.hitCount` is never incremented. Aliases today come from bill commits (LLM_SUGGESTED, auto-approved because the owner reviewed the plan) and from the owner typing them. The catalogue does *not* currently get smarter when it gets something wrong.
2. **`ResolutionMethod` has a schema/TypeScript mismatch.** The Prisma enum has 8 members and omits `RECOVERED`; the TypeScript union has 9 and includes it, and `rank.ts` can produce it. The write in `core.ts` casts `as never` to bypass the mismatch — so persisting a RECOVERED line would send an invalid enum value to Postgres. Worth fixing before the morphology tier ever wins a line that gets ordered.

Also dead: `ResolutionMethod.EMBEDDING` and `.LLM` are never produced (but `EMBEDDING` *is* rendered by the orders UI as "matched on meaning" — an unreachable state), and `POLICY_FLOOR = 0.45` in `core.ts` is declared with a doc comment and referenced nowhere.
